## 3. Critical issues

### C1. Operational API is unauthenticated and CORS is fully open
- **Evidence:** `backend/src/index.ts` uses `app.use(cors())`; no auth middleware; all four routes are public.
- **Impact:** Anyone who can reach port 4000 can read intelligence/scenario data and trigger expensive simulations. `GET /db-test` exposes schema errors and sample rows. CORS lets any website invoke the API from a victim’s browser.
- **Fix:** Require verified Supabase JWTs, enforce roles/tenant scope, restrict origins, add rate limits, and remove/gate `/db-test`.

### C2. Forecast feature index is off by one day
- **Evidence:** `backend/src/services/intelligenceService.ts:383`, `backend/src/services/scenarioService.ts:513`, and `frontend/src/data/hospitalIntelligence.ts:652` call `buildBaseFeatures(simulated, simulated.length - 1)`.
- **Impact:** Each forecast step is built for the last observed date rather than the next date, excludes the newest demand from `lag1`/rolling windows, and then assigns that prediction to the following date. Forecast dates, lag values, and day-of-week/month features are misaligned; risk/stock-out days inherit the error. This is the highest-impact correctness defect in the engine.
- **Fix:** Use `simulated.length`; add date/lag alignment tests and a deterministic forecast fixture.

### C3. Redistribution can promise the same surplus multiple times
- **Evidence:** `backend/src/services/scenarioService.ts:758–804` selects donors once, never decrements `projected_remaining_stock`, and does not rerun the simulation or summaries.
- **Impact:** One donor’s surplus can be promised to several recipients; feasibility is overstated. Recipient risk, shortage, and totals remain pre-transfer. Partial/multi-donor transfers are not supported.
- **Fix:** Decrement donor surplus as promises are made; support partial/multi-donor allocation; rerun risk and summary after transfers; expose transfer time/cost/capacity constraints.

### C4. Database is not reproducible from the repository
- **Evidence:** no `.sql`/migrations/seed files; only a “reference only” schema block in `README.md:528–591`.
- **Impact:** A fresh environment cannot be provisioned reliably; column/constraint/RLS drift is invisible until runtime. Scenario simulation fails without the seed row, and intelligence silently falls back to synthetic data.
- **Fix:** Add versioned migrations, seed scripts, RLS policies, indexes, and a CI schema check.

### C5. Documented frontend environment setup breaks startup
- **Evidence:** `frontend/src/lib/supabase.ts:4` requires `VITE_SUPABASE_PUBLISHABLE_KEY`; `frontend/.env.example:8` defines `VITE_SUPABASE_ANON_KEY`.
- **Impact:** Following the repository’s setup instructions throws before React renders. New contributors cannot run the app without guessing the variable name.
- **Fix:** Standardize on one name, update the example and README, and document migration for Supabase’s anon/publishable key terminology.

### C6. Service-role credential is the only database control
- **Evidence:** `backend/src/utils/supabase.ts` initializes with `SUPABASE_SERVICE_ROLE_KEY`; the API has no authorization.
- **Impact:** Any API compromise yields full-table read/write capability even if RLS is enabled. There is no least-privilege separation between read and write paths.
- **Fix:** Use a restricted server role, enforce API authorization, keep service-role operations isolated, and add audit logging. Never expose the key to the frontend.

## 4. High issues

### H1. Scenario “affected” IDs are network-wide, not scenario-specific
- **Evidence:** `scenarioService.ts:664–665` derives IDs from every result; `buildSummary` discards them with `void` but still returns the full arrays.
- **Impact:** Every scenario reports all 5 hospitals and all medicines as affected, undermining triage and the UI’s impact story.
- **Fix:** Compute affected sets from `supplier_disrupted`, actual risk, or explicit scenario targeting.

### H2. Disruption mechanics do not model supply
- **Evidence:** `scenarioService.ts` applies uniform demand multipliers; transport delay only extends `windowDays`; supplier failure only adds text/alternate-supplier advice; no resupply is ever modeled.
- **Impact:** “Supplier failure” does not stop deliveries because deliveries are absent; “transport delay” does not reduce inbound stock; “hospital disruption” does not target a facility. Scenario distinctions are largely cosmetic, which can mislead planning.
- **Fix:** Add scheduled deliveries, supplier capacity, lead-time distributions, per-facility targeting, and reduced inbound quantities.

### H3. Cascade/network impact is claimed but not implemented
- **Evidence:** no dependency graph or propagation code; only independent per-tuple projection plus one redistribution pass.
- **Impact:** README and scenario copy imply cascading effects that the model cannot produce. Decisions may over-trust network-level conclusions.
- **Fix:** Implement an explicit supplier→medicine→facility graph with time-phased propagation, or remove the cascade claim.

### H4. Scenario simulation has no fallback and fails without seeded data
- **Evidence:** `scenarioService` requires a matching `scenarios` row and non-empty `inventory`; Dashboard has no cached/local result path.
- **Impact:** The headline demo breaks on a fresh database or backend outage, while Intelligence keeps working via synthetic fallback. This produces an inconsistent demo experience.
- **Fix:** Add a deterministic scenario fallback or ship versioned seed/migrations; surface a clear “demo data” state.

### H5. API base URLs are hardcoded to localhost
- **Evidence:** `frontend/src/api/scenarios.ts:8`, `frontend/src/data/hospitalIntelligence.ts:72`; `VITE_API_BASE_URL` is unused.
- **Impact:** A deployed frontend cannot reach its backend without editing source; previews and containerized deployments fail.
- **Fix:** Read the environment variable with a safe default and validate at startup.

### H6. Uploads are session-only but presented as a document workflow
- **Evidence:** `DocumentsPage.tsx:71,198,221` stores uploads in React state with object URLs; no upload API/storage.
- **Impact:** Refresh loses files and records; scheme document readiness is not durable. Users may believe documents were saved.
- **Fix:** Label clearly as a demo, or add authenticated storage with validation, virus scanning, retention, and consent.

### H7. No automated tests for financial/clinical-adjacent logic
- **Evidence:** no test files/scripts; only compiler checks.
- **Impact:** Regressions in ridge math, lag alignment, risk thresholds, redistribution, and API shape are undetected. The off-by-one and double-spend defects are exactly the class tests would catch.
- **Fix:** Unit tests for features/model/metrics, scenario fixtures, redistribution invariants, API contract tests, and frontend smoke tests.

### H8. Browser fallback silently masks backend failure
- **Evidence:** `hospitalIntelligence.ts:102–103` catches every error and returns local results; 4.5 s timeout.
- **Impact:** Users may see plausible numbers without knowing the backend/Supabase is down. Two model implementations can drift.
- **Fix:** Surface a prominent degraded-mode banner/source badge, log telemetry, and consolidate shared logic.

### H9. No request validation or central error handling
- **Evidence:** `POST /api/scenarios/simulate` accepts any body; routes catch and return generic 500s; no middleware.
- **Impact:** Invalid input becomes opaque 500s; clients cannot distinguish 400/404/503; debugging requires server logs.
- **Fix:** Add schema validation, typed error codes, an error middleware, and request IDs.

### H10. No data-privacy or real-data readiness
- **Evidence:** demo citizen state in `localStorage`; no consent/retention/audit; uploads in browser memory; no RLS/API authorization.
- **Impact:** Real patient/documents data would be unsafe to introduce. Current design cannot satisfy health-data handling obligations.
- **Fix:** Define data classification, consent, retention, encryption, access control, audit trail, and breach procedures before any real data.

### H11. MAPE is computed incorrectly
- **Evidence:** `mlForecast.ts:424–453` sums percentage error only for non-zero actuals but divides by all `N`.
- **Impact:** Displayed error understates performance gaps on intermittent-demand series.
- **Fix:** Divide by the count of non-zero actuals or use a zero-safe metric (MASE/sMAPE), and document the choice.

### H12. Scheme records all assert “verified” without verification evidence
- **Evidence:** `frontend/src/data/schemes.ts`; all 10 records use `info_status: "verified"`.
- **Impact:** Users may read “verified” as a guarantee of current eligibility/benefits. No source snapshots, dates, or automated checks are in the repo.
- **Fix:** Add source URLs/dates/reviewers, separate “content verified” from “eligibility determined,” and run link/content checks.

## 6. Low issues and technical debt

- Unused `ping()` in `frontend/src/types/api.ts`.
- Unused `ML_SERVICE_URL` and `VITE_API_BASE_URL`.
- Env examples say Supabase is “reserved for a later phase - not used yet,” which is stale.
- Empty `controllers/`, `middleware/`, ML `models/`, `routers/`, `services/` directories.
- Duplicate legacy/structured fields in domain types and data.
- README/architecture claims exceed implementation (cascade, Copilot Q&A, one-click save, “no auth/ML/DB”).
- `Navbar` hardcodes English “Hospital Intel” instead of using translations.
- `/db-test` “counts” are counts of the first 5 rows, not table counts.
- No repository license/contribution guide/security policy.
- No changelog or release/version strategy.
- No frontend error boundary.
- No favicon/metadata audit; no external font or analytics, which is privacy-positive.
- Build output not checked into Git (correct), but no deploy artifact pipeline exists.

## 7. Recommended test strategy

| Layer | Priority tests |
|---|---|
| Unit — forecasting | Feature construction, lag/date alignment at `i=n`, standardization, ridge solution, prediction inversion, metrics (including zeros), risk thresholds |
| Unit — scenarios | Each disruption type, window calculation, affected IDs, recommendation ordering, redistribution invariants (no over-allocation), summary totals |
| Contract | `POST /simulate` request/response, `GET /summary` shape, error codes, frontend unwrapping |
| Integration | Seeded Supabase (or ephemeral Postgres) migrations + API runs; empty-DB fallback; missing scenario |
| Frontend | Route guards, fallback badge, dashboard error/loading, upload loss warning, language switching, voice error mapping |
| Non-functional | Authz tests, CORS checks, rate limits, load test on 18k demand rows, accessibility, bundle budgets |

Minimum viable suite before calling this pilot-ready: forecast alignment tests, redistribution invariants, API contract tests, and an authz test proving unauthenticated calls are rejected.
